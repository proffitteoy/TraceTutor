# 接口与闭环设计

> 本文用于把 [架构设计.md](./架构设计.md)、[agent设计.md](./agent设计.md)、[pgsql设计.md](./pgsql设计.md)、[SQLite设计.md](./SQLite设计.md) 串成一套可实现的闭环。

## 1. 解决的问题

当前几份设计文档分别讲清了：

- 系统分层
- Agent 编排
- 题目资产建模
- 学习状态建模

但如果没有一份总装配图，后续实现时仍然容易出现这些问题：

- 前端直接假设数据库结构
- Agent 输出和 API 输入对不上
- PgSQL 与 SQLite 的主键、状态边界不统一
- 新题导入、解题、复习、状态回写各自成文，缺少端到端收束
- 出错时不知道该在哪一层降级

本文的目标就是把这些地方补成闭环。

## 2. 系统边界总览

TraceTutor 统一采用五层结构：

```text
Iris 前端
  ↓
扣子 Agent / Workflow
  ↓
自有 API / Tool Gateway
  ↓
PgSQL 题目资产库
  + 
SQLite 用户状态库
```

每层只做自己的事：

| 层 | 负责什么 | 不负责什么 |
|:---|:---|:---|
| Iris | 输入题目、展示答案、卡片渲染、提交用户作答 | 不直接查库，不拼复杂业务规则 |
| 扣子 Agent | 意图理解、Workflow 编排、教学输出组织 | 不直接写 SQL，不直接改数据库 |
| API / Tool Gateway | 查询计划校验、安全执行、规则校验、状态写回、日志落库 | 不承担前端渲染，不承担自由生成式教学 |
| PgSQL | 题目、答案、解析、知识点、方法、相似关系、变式关系 | 不存用户掌握度和复习计划 |
| SQLite | 做题记录、掌握状态、复习调度、上下文摘要、运行日志 | 不复制完整题库和解析资产 |

## 3. 统一主键与引用规则

为了闭环，所有文档统一采用下面的引用原则：

| 对象 | 主存储 | 标识 |
|:---|:---|:---|
| question | PgSQL | `question_id` |
| knowledge point | PgSQL | `knowledge_point_id` |
| method | PgSQL | `method_id` |
| learning session | SQLite | `session_id` |
| question attempt | SQLite | `attempt_id` |
| review schedule | SQLite | `schedule_id` |
| workflow run | SQLite | `workflow_run_id` |
| pending state delta | SQLite | `pending_state_delta_id` |

强约束：

- SQLite 记录题目相关状态时，只保存 `question_id` 引用，不复制整题正文。
- Agent 输出中只允许引用工具已经返回的 `question_id`、`attempt_id` 等对象。
- 前端展示若需要完整题目内容，必须通过 Agent 输出或 API 渲染结果获得，不能自己拼库查询。

## 4. 三类核心契约

系统真正需要闭合的是三类契约。

### 4.1 Iris → Agent 的输入契约

前端发给扣子的内容不应该是数据库语义，而应该是用户任务语义：

```json
{
  "session_id": "S123",
  "user_id": "U123",
  "input_mode": "new_question",
  "user_text": "我想复习之前错过的极限题，再来一道换方法的",
  "attachments": [],
  "active_question_id": null
}
```

重点：

- 前端传的是用户输入和当前会话上下文
- 前端不传 SQL、不传题库筛选条件、不直接决定状态写回

### 4.2 Agent → API 的查询计划契约

Agent 只能输出查询计划，不允许输出 SQL：

```json
{
  "intent": "REVIEW_AND_VARIANT",
  "task_types": [
    "REVIEW_OLD_QUESTION",
    "GENERATE_SIMILAR_QUESTION",
    "METHOD_TRANSFER"
  ],
  "state_queries": [
    {
      "tool": "state.query_wrong_questions",
      "filters": {
        "knowledge_area": "极限",
        "state_labels": ["weak", "reviewing"]
      },
      "limit": 5
    }
  ],
  "asset_queries": [
    {
      "tool": "asset.search_same_knowledge_different_method",
      "base_question_id": "Q123",
      "difficulty_policy": "near",
      "limit": 3
    }
  ]
}
```

API 必须对这份计划做：

- 工具白名单校验
- 参数形态校验
- limit 上限校验
- 用户权限与会话归属校验
- 降级策略选择

### 4.3 API → Agent 的工具结果契约

工具返回不能只是“查到了”，而要让 Agent 能解释为什么能用：

```json
{
  "items": [
    {
      "question_id": "Q456",
      "stem": "...",
      "knowledge_points": ["函数极限"],
      "methods": ["泰勒展开"],
      "difficulty_level": 3,
      "reason": "与旧题同属极限，但主方法不同，可用于方法迁移。"
    }
  ],
  "meta": {
    "source": "pgsql",
    "status": "ok"
  }
}
```

没有 `reason`、没有 `status`、没有 ID 的结果，不足以支撑教学输出和后续日志解释。

## 5. 四条闭环主流程

### 5.1 题目导入闭环

```text
原始题目来源
  ↓
PgSQL staging
  ↓
清洗 / 去重 / 抽取题干
  ↓
标注知识点 / 方法 / 结构
  ↓
生成答案 / 解析 / 相似边 / embedding
  ↓
审核
  ↓
status = active
  ↓
进入正式召回
```

闭环条件：

- 未审核题目不得进入正式复习与正式推荐
- 所有导入题必须可追溯来源
- 导入失败必须保留批次和错误记录

### 5.2 新题解答闭环

```text
Iris 提交新题
  ↓
Main Agent 判断为 NEW_QUESTION_SOLVE
  ↓
API 读取 agent_bootstrap_context
  ↓
PgSQL 查相似题 / 方法 / 知识点
  ↓
主 Agent 生成答案与变式题
  ↓
用户提交作答或接受讲解
  ↓
API 写 question_attempt / question_attempt_tag
  ↓
规则层生成 pending_state_delta
  ↓
校验通过后更新 mastery_state / review_schedule / context_summary
```

闭环条件：

- 新题过程必须最终落到用户状态变化，而不只是“给出答案”
- 如果用户输入的新题值得沉淀，只能先进入 PgSQL 的 `draft/imported`，不能直接 `active`

### 5.3 复习闭环

```text
Iris 请求复习 或 系统触发复习
  ↓
API 从 SQLite 读取薄弱项 / 到期复习 / 错因模式
  ↓
Agent 生成复习查询计划
  ↓
PgSQL 召回同知识点题 / 方法迁移题 / 旧题 review 资产
  ↓
主 Agent 组织复习包
  ↓
用户作答
  ↓
API 判题并写 review_event / question_attempt
  ↓
规则层更新 mastery_state / error_pattern_state / review_schedule
```

闭环条件：

- 复习对象不只是一道题，也可以是方法、知识点、思维模式或错因模式
- 复习后必须更新下次复习时间，否则无法形成调度闭环

### 5.4 状态写回闭环

```text
Agent 生成 state_delta 建议
  ↓
写入 pending_state_delta
  ↓
规则层校验
  ↓
通过：更新正式状态表
  ↓
记录 mastery_event / local_event_log
  ↓
更新 context_summary / agent_memory_item
  ↓
下轮 Agent 启动时重新读取
```

闭环条件：

- Agent 只提建议，不直接修改正式状态
- 所有正式状态变化都必须有 `attempt_id`、`review_event_id` 或等价证据

## 6. 降级与异常闭环

系统不能只设计成功路径，还要设计失败时如何闭合。

| 异常 | 降级策略 | 仍需完成什么闭环 |
|:---|:---|:---|
| 查不到用户历史状态 | 退化成普通讲解模式 | 仍记录本轮 session 与日志 |
| 查不到同类题 | 生成草稿题或只做旧题 review | 草稿题不得进入 active |
| 方法标签不确定 | 只按知识点召回 | 在日志中标记 `method_confidence = low` |
| 状态写回失败 | 正常给用户返回答案 | 保留 `pending_state_delta` 待重试 |
| 工具结果过长 | 先压缩再进主 Agent | 原始结果以 ID 或日志方式可回查 |

## 7. 最小实现闭环

如果按 MVP 推进，不需要一开始把所有设计一次性做完，但至少要保证下面这条链是通的：

```text
用户输入
  ↓
Agent 产出查询计划
  ↓
API 执行有限工具
  ↓
PgSQL / SQLite 返回结构化结果
  ↓
Agent 组织答案
  ↓
API 记录 attempt / workflow_run / tool_call_log
  ↓
规则层更新掌握度与复习计划
```

MVP 缺一不可的文件落点：

- `db/pgsql/migrations/`：题目资产最小建表
- `db/sqlite/migrations/`：用户状态最小建表
- `apps/api/`：查询计划执行、状态写回校验
- `agents/coze/`：Prompt、Workflow、工具 schema
- `apps/iris/`：输入与渲染
