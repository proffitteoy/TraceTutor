# 数据库协作边界

本文用于约束 PgSQL 与 SQLite 两位协作者的并行开发边界。目标是让两个数据模块各自高内聚，通过 API 契约协作，而不是互相引用实现细节。

## 1. 所有权

| 协作者 | 主要修改范围 | 业务所有权 | 不应修改 |
|:---|:---|:---|:---|
| PgSQL 协作者 | `db/pgsql/**`、`docs/pgsql设计.md` | 题目、答案、解析、知识点、方法、相似关系、审核状态 | SQLite 表、用户掌握度、复习计划、Iris 组件 |
| SQLite 协作者 | `db/sqlite/**`、`docs/SQLite设计.md` | 作答事实、掌握状态、复习调度、上下文、工作流日志 | PgSQL 题目正文、相似度资产、Iris 组件 |
| API 协作者 | `apps/api/**`、跨层接口文档 | 查询计划校验、工具路由、规则写回、错误映射 | 让 Agent 或 Iris 直接执行 SQL |
| Iris 协作者 | `apps/iris/**` | 用户输入、教学卡片渲染、作答交互 | 数据库迁移、掌握度算法、题目召回 SQL |

如果一项修改同时影响两套数据库，先修改 `docs/接口与闭环设计.md` 中的跨层契约，再由两个协作者分别在自己的目录实现；不要由其中一人跨目录直接完成全部改动。

## 2. 唯一耦合面

两套数据库只通过 `apps/api` 暴露的业务工具协作：

```text
PgSQL 题目资产工具 ─┐
                    ├─ apps/api / Tool Gateway ─ Agent ─ Iris
SQLite 状态工具 ───┘
```

SQLite 工具由 `apps/api/src/adapters/sqlite-tool-execution.ts` 适配，
PgSQL 工具由 `apps/api/src/adapters/pgsql.ts` 适配，API 使用
`CompositeToolExecutionPort` 组合两个端口；Agent 不持有任何数据库地址。

允许共享的是稳定标识和业务结果：

- `question_id`
- `knowledge_point_id`
- `method_id`
- `session_id`
- `attempt_id`
- `workflow_run_id`

禁止共享的是：

- 数据库连接对象
- ORM model / generated client
- 表级 repository
- 跨数据库外键
- 可执行 SQL 字符串

SQLite 可以保存 `question_id` 等资产引用，但不复制完整题目、答案或解析，也不对 PgSQL 建跨库外键。引用有效性由 API 在写入前校验。

## 3. 事务与失败边界

PgSQL 与 SQLite 不组成分布式事务。一次教学流程按事实顺序推进：

```text
1. 从 PgSQL 读取已审核题目资产
2. Agent 组织教学结果
3. SQLite 记录用户真实作答事实
4. 规则层生成并校验 pending_state_delta
5. SQLite 应用正式状态变化
```

某一步失败时：

- PgSQL 召回失败：降级为讲解或旧题回顾，不伪造 `question_id`。
- SQLite 状态查询失败：仍可返回普通讲解，但要标记为无个性化上下文。
- SQLite 写回失败：教学结果可以返回，状态建议保持 pending 并记录失败原因。
- 题目沉淀失败：生成题只在当前会话可用，不进入 `active` 召回池。

## 4. 协作者交付清单

每位数据库协作者交付时至少提供：

1. 自己目录内的迁移或脚本。
2. 对应目录 README 中的真实执行与回滚说明。
3. 对外业务工具需要的输入、输出字段。
4. 主键、唯一约束、状态枚举和索引说明。
5. 本模块验证结果，以及尚未进行的跨层验证。

涉及公共 ID 或工具响应变更时，必须在 PR 或交付说明中列出兼容性影响；不能让 Iris 读取底层表结构来临时绕过契约。

## 5. Iris 的适配点

Iris 只依赖 `apps/iris/lib/contracts.ts` 中的 `LearningRequest` 和 `LearningResponse`。当前只提供 `HttpGateway` 请求 `/agent/chat`；未配置网关时前端明确禁用发送，不用 Demo、Mock 或本地规则伪造结果。

后续 PgSQL、SQLite 或 API 实现变化，只要保持这份渲染契约兼容，前端无需同步修改。需要新增卡片类型时，先在 Agent 输出规范和 HTTP 契约中定义，再扩展前端联合类型与渲染组件。

数据库协作者通过 `apps/api/src/ports.ts` 的两个高层端口交付能力：

- `ToolExecutionPort`：15 个运行期白名单业务工具；
- `QuestionIngestionPort`：JSONL 批量初始化、用户新题自动入库、标签候选和人工复核事务。

端口只接受结构化业务参数；不得把连接对象、ORM model、表级 repository 或 SQL 字符串暴露给 API 以外的层。题目摄取的具体事务和幂等要求见 [题库摄取与审核.md](./题库摄取与审核.md)。

SQLite 内部服务使用 `Authorization: Bearer <service-token>`，并再次核对工具 `input` 与 `RequestContext` 的 `user_id`、`session_id`。Iris 与模型 API 不得持有这个内部 token。

### 当前 Runtime 依赖的写入结果

`state.write_attempt_result`：

```json
{
  "result": {
    "attempt_id": "A123",
    "pending_state_deltas": [
      {
        "pending_state_delta_id": "PSD123",
        "state_delta": {
          "target_type": "knowledge_mastery",
          "target_id": "KP123",
          "proposed_change": 0.1,
          "reason": "规则层根据独立正确作答生成",
          "evidence": {
            "question_id": "Q123",
            "attempt_id": "A123",
            "judgement": "correct",
            "knowledge_point_ids": ["KP123"],
            "method_ids": ["M123"]
          }
        }
      }
    ]
  },
  "meta": {
    "source": "sqlite",
    "status": "ok",
    "reason": "作答事实与 pending delta 已写入"
  }
}
```

`state.write_review_result` 使用相同的 `pending_state_deltas` 结构，并额外返回 `review_event_id`。

`state.apply_state_delta` 必须：

- 校验 `pending_state_delta_id` 属于当前用户和会话；
- 再次核对 evidence 引用；
- 幂等应用；
- 返回 `applied`、`rejected` 或仍为 `pending` 的业务结果。

`asset.create_question` 必须在同一事务内补齐题目资产、写入自动批准证据并切换为 `active`，返回真实 `question_id`。Runtime 只有在工具成功返回 ID 后，才允许模型把生成题渲染为题目卡。
