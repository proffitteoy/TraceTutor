**前端 Iris 负责交互展示；扣子负责 Agent 编排；PgSQL 存稳定题目资产；SQLite 存用户学习状态；主 Agent 总控流程；子 Agent 只负责把用户意图翻译成可执行查询计划。**

核心不是“做一个 JSON”，而是做一个**题目—状态—召回—生成—复习**的闭环系统。JSON 只是中间数据格式，不是系统本体。

顶层架构应当这样理解：

```text
Iris 前端
  ↓
输入层
  ↓
主 Agent
  ↓
意图理解子 Agent
  ↓
SQLite 状态查询 + PgSQL 题目召回
  ↓
主 Agent 组织生成
  ↓
答案 / 同类题 / 复习题 / Review
  ↓
前端渲染 + 状态回写
```

更准确地说，**扣子不是传统意义上的后端**。传统后端应该负责数据库、接口、权限、状态一致性、任务调度。扣子更适合承担的是：

```text
Agent 编排层 / Workflow 层 / 对话控制层
```

所以实际后端结构应该是：

```text
Iris 前端
  ↓
扣子 Agent 编排层
  ↓
工具 / API 层
  ↓
PgSQL + SQLite
```

也就是说，扣子不要直接变成“数据库后端”，而是通过插件、HTTP API、工作流节点去调用你自己的数据服务。



数据层可以分成两类。

第一类是 **PgSQL：纯题目数据层**。

它存放相对稳定、可复用、可被召回的题目资产，例如：

```text
题目原文
标准答案
解析
知识点标签
方法标签
难度
题型
来源
相似题关系
题目结构特征
适用阶段
```

PgSQL 的定位是：

```text
题库资产库
知识点资产库
方法资产库
召回候选池
```

它不应该承担太多“某个学生现在学到哪里了”的状态逻辑。否则题库数据和用户状态会混在一起，后面会很难维护。

第二类是 **SQLite：用户状态层**。

它存放可变的、和具体用户绑定的学习状态，例如：

```text
用户做过哪些题
每道题是否答对
错因是什么
当前掌握度
最近复习时间
下一次复习时间
知识点熟练度
方法熟练度
题型熟练度
新旧知识点关联记录
review 记录
```

SQLite 的定位是：

```text
学习轨迹库
状态记忆库
复习调度库
用户画像库
```

早期原型用 SQLite 合理，因为简单、轻量、容易迁移。但如果以后变成多人系统，SQLite 最终大概率要迁移到 PgSQL 的用户状态表，或者至少拆成 PostgreSQL + Redis / event log。



Agent 层结构是：

```text
主 Agent：总控状态与流程
子 Agent：意图理解 + 查询计划生成
工具层：执行 SQLite 查询、PgSQL 召回、答案生成、状态回写
```

其中，**主 Agent 不应该亲自判断所有查询细节**，否则 prompt 会越来越臃肿。它只负责判断当前任务属于哪一类：

```text
新题解答
同类型题生成
复习触发
旧题 review
知识点迁移
方法互通
状态更新
```

然后调用子 Agent。

子 Agent 的职责很窄：

```text
把用户输入转成查询计划。
```

例如用户说：

```text
我想复习一下之前错过的极限题，再出一道类似但换方法的。
```

子 Agent 应该输出类似：

```text
意图：复习 + 同知识点新题 + 方法迁移
需要查 SQLite：用户历史错题、极限相关、最近掌握度低的记录
需要查 PgSQL：极限知识点下，与旧题相似但方法不同的新题
需要调用 review：旧题回顾
需要生成：一道新题 + 对比解析
```

注意，这里的 JSON 只是**查询计划的表达格式**。真正重要的是它背后的状态机和相似度定义。

---

目前的系统可以分成两个主流程。

第一个是 **新题流程**。

```text
用户输入一道新题
  ↓
主 Agent 判断为“新题”
  ↓
解答题目
  ↓
生成同类型题
  ↓
抽取知识点、方法、题型、错误风险
  ↓
写入 SQLite 状态
  ↓
必要时把题目结构写入 PgSQL 或候选题库
  ↓
前端展示：原题解答 + 同类题 + 状态变化
```

这个流程的核心不是“答题”，而是：

```text
答完之后如何改变用户状态。
```

例如：

```text
用户掌握了哪个知识点？
暴露了哪个方法缺口？
这道题和旧题有什么关系？
下次复习应该推什么题？
```

所以新题流程应该产生三类结果：

```text
1. 答案结果：这题怎么做
2. 题目结果：同类型题 / 变式题
3. 状态结果：用户学习状态如何变化
```

第二个是 **复习流程**。

复习流程不只是“再出一道旧知识点题”，而是三个方向：

```text
同知识点新题
新知识点与旧知识点方法互通
调用旧题 review
```

也就是说，复习不是简单重复，而是做三件事：

```text
巩固：同知识点再练
迁移：同方法迁移到新知识点
回看：调用旧题解释用户当时为什么错
```

所以复习流程应该是：

```text
用户请求复习 / 系统触发复习
  ↓
查询 SQLite：用户薄弱知识点、旧题、错因、复习间隔
  ↓
查询 PgSQL：候选复习题
  ↓
主 Agent 决定复习策略
  ↓
输出：
  - 一道同知识点新题
  - 一道方法迁移题，必要时
  - 旧题 review
  ↓
写回 SQLite：本次复习表现、掌握度变化、下次复习时间
```

---

除了“新题流程”和“复习流程”，系统还必须再补上两个闭环，不然后面实现时会断在边界上。

第三个是 **题目沉淀闭环**。

这里回答的是：用户输入的新题、AI 临时生成题、外部导入题，什么时候只是会话候选题，什么时候能变成正式题库资产。

```text
用户输入新题 / 系统生成临时题 / 外部批量导题
  ↓
进入 PgSQL draft / imported / staging
  ↓
抽取题干、答案、解析、知识点、方法、结构
  ↓
生成相似边与候选关系
  ↓
审核
  ↓
只有 status = active 才能进入正式召回
```

这里有一个必须钉死的业务边界：

```text
会话内可用
≠
正式题库可召回
```

也就是说：

```text
AI 临时生成题可以服务当前 session
但不能自动进入全局 active 召回池
```

第四个是 **状态写回闭环**。

前面说“写回 SQLite”，但这里不能理解成主 Agent 直接改最终状态。  
真正应该是：

```text
主 Agent 生成 state_delta 建议
  ↓
API / 规则层校验
  ↓
先写 pending_state_delta
  ↓
验证证据是否充分
  ↓
再更新 mastery / review / error pattern / context summary
```

判断“证据是否充分”时，至少要看：

```text
是否存在真实作答记录
是否存在题目 ID
是否有判题结果
是否有知识点 / 方法标签
是否属于允许更新的状态类型
```

这样做的目的不是增加复杂度，而是防止：

```text
模型一句“用户似乎掌握了”
就直接污染长期学习状态
```

---

你说得最关键的一点是：

**状态流转和相似量化不是一个 JSON 可以解决的。**

这个判断是对的。

JSON 最多解决：

```text
数据怎么传
查询计划怎么表达
节点之间怎么通信
```

但它解决不了：

```text
什么叫掌握
什么叫相似
什么叫同类型
什么叫方法互通
什么叫该复习
什么叫状态转移
```

这些必须是系统规则。

所以你的核心系统应该抽象成两个引擎：

```text
状态引擎
相似度引擎
```

暂时可以不实现得很复杂，但架构里必须预留。

状态引擎负责：

```text
用户从“未接触”到“初学”到“掌握不稳”到“稳定掌握”的变化
```

例如：

```text
unseen
  ↓
attempted
  ↓
understood
  ↓
weak
  ↓
reviewing
  ↓
stable
```

每次用户做题，状态都要变化。

相似度引擎负责回答：

```text
两道题为什么相似？
它们是知识点相似，还是方法相似，还是结构相似，还是表面形式相似？
```

这里至少要拆成四类相似：

```text
知识点相似
方法相似
题型结构相似
解题路径相似
```

例如两道题都考“极限”，这是知识点相似。

两道题一个是数列极限，一个是函数极限，但都用“夹逼定理”，这是方法相似。

两道题都需要“先构造辅助函数，再用单调性”，这是解题路径相似。

这三种相似不能混成一个 embedding 分数。否则系统会失去教学价值。

---

把这些部分串起来后，系统的最小业务闭环应该是：

```text
输入题目 / 请求复习
  ↓
Agent 判断任务
  ↓
查询 SQLite 获取“这个学生现在需要什么”
  ↓
查询 PgSQL 获取“系统当前有哪些资产可用”
  ↓
组织答案 / review / 新题 / 迁移题
  ↓
记录作答事实
  ↓
规则层校验状态变化
  ↓
更新下次复习与短期记忆
```

如果少了最后三步，这个系统就会退化成：

```text
会讲题的问答机器人
```

而不是：

```text
可持续跟踪学习状态的教学系统
```
